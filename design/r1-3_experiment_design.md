# R1-3 追加実験の設計案 (draft v0.4.2, 2026-10-02)

## 1. 目的

R1-3 の 2 つの要求に、1 つの実験で答える。

- **構成要素ごとの分析**: Tier A から構成要素を 1 つずつ外して比べ、どの要素が効いているかを見る。
- **ベースラインとの比較**: 構造化した issue を使わず、チャットで逐次指示する進め方をベースラインとして置く。投稿版の Limitations が挙げたものと同じ。

## 2. 条件

| 条件 | 課題の分割 | 人間の承認ゲート | issue ファイル・handover・委任境界文書 | 数学定義 | 作業用文書 (B(0,n) スキーマ、Layer 指示) |
|---|---|---|---|---|---|
| **A** (Full) | 8 段階 | あり | あり | 改訂版 | あり |
| **G−** (No gate) | 8 段階。I01–I08 を一度に提示 | なし。最終レビューのみ | あり | 改訂版 | あり |
| **F−** (No files) | 8 段階 | あり | なし。チャットで逐次指示 | 改訂版 | あり。A と同じファイルを `docs/math/` に置く |
| **C** (One-shot) | なし | なし | なし | 改訂版 | なし |

- 数学定義は、4 条件とも改訂版の 3 ファイル (X-base と同一の blob) を使う。
  - `Cn1_definition.md`: ce84883
  - `C_inhomogeneous_definition.md`: 84944ee
  - `C_coboundary_definition.md`: fc1b246
- スキーマと Layer の指示は、数学定義とは別のファイルに分け、A、G−、F− にだけ配布する。
- これにより、既存の run にあった食い違いを新規 run では解消できる。既存の A は旧版の文書 (8365814、afb0573、49a9ebc) を、C は改訂版を使っていた。両者は数学的には同じ内容 (著者確認済み) だが、文面と同梱された情報が異なっていた。

この表から読める差は次の 3 つ。

- **A と G− の差**: 人間のゲートの効果。分割と文書は同じ。
- **A と F− の差**: 課題をファイルで構造化し記録することの効果。ゲートと分割は同じ。
- **G− と C の差**: 分割とスキーマによる文脈の効果。

### G− の詳細

- I01–I08 の issue ファイルを、順番を指定して一度に渡す。
- 次のように指示する。「各段階の受け入れ基準を自分で確認しながら、最後まで進めよ。途中で止まって承認を求めるな」
- 人間は最終成果物だけを見る。
- 却下しても修正の機会は与えない。却下はそのまま結果として記録する。

### F− の詳細

- **方式は (i) とする。** A と同じエージェント環境を使い、Worker が自分でコードを書いて実行する。
  - Web チャットのように、人間がコードを実行する方式 (ii) は採らない。採ると、Worker が自分で実行できるかどうかという要因まで変わり、差の原因を切り分けられなくなるため。
- 1 つのセッションで、I01 から I08 を順に指示する。
- 指示の情報量は A の issue と同じにする。
  - Manager AI が issue の内容をチャット用の文面に直す。
  - 人間が確認してから貼る。
  - 人間は Worker に直接指示しない、という既存のルールに従う。
- Worker に渡さないもの: issue ファイル、handover、`ai_trust_policy.md`、ファイル上の承認ルール、Git の運用ルール。
- 数学文書と B(0,n) のスキーマは、A と同じファイルを `docs/math/` に置く。外すのは作業の進め方に関わる文書だけで、領域の知識は外さない。
- 承認や修正は、チャットのメッセージで伝える。
- **Worker には Git を使わせない。**
  - 作業ディレクトリは Git 管理の外に置く。
  - run が終わったあと、人間が作業ディレクトリとチャットログをまとめて公開ブランチに保存する。
  - Worker からは記録が見えないので、結果には影響しない。

### 繰り返し実行 (v0.4 で追加)

| モデル | 条件 | 回数 | 名前 |

- 独立性の確保:
  - 毎回、新しいワークスペースと新しいセッションで行う。
  - 過去の履歴は参照させない。
  - 前回の run のディレクトリも参照させない。
- 報告の仕方:
  - 「k/3 回」のように記述的に書き、統計的な主張はしない。
  - 繰り返したのは Luna の C と G− だけであることを明記する。
  - Copilot CLI では temperature を指定できないので、既定の設定でのばらつきとして報告する。

- **公開**: Worker のコミットは、その日のうちに公開リポジトリへ push する。
- **プロンプト**: 条件ごとに事前に確定し、実行前にコミットする。どのモデルにも同じ文面を使う。

- 記法の読み違いを、観察項目に加える (2026-10-02)。
  - 注記の意図: 変形は gb·κ であり、κ を含めた全体が parity 1 をもつ。gb 自体はスカラーである。
  - Worker の読み方: Luna は C の 3 回すべてと G− の 2 回で、gb 自体が奇だと読んでいる。
  - この書き方は数学では普通であり、文脈から補正できるべきもの。補正できないことも、丸投げ (one-shot) の問題として扱う。
  - 配布文書は直さない。条件をそろえるため。A と F− で読み違いが起きた場合は、それが分かった時点で、どの段階であっても修正指示を出して訂正する。修正指示は Manager AI が起草し、人間が確認してから出す。この介入は、種類「記法の明確化」として記録する。
- A と F− では、Manager AI の承認文を、Worker が挙げた各項目に 1 つずつ応答する形にする。人間は、応答していない項目がないかを確認する。根拠は、旧 thm01-05 でパリティの論点が共通の承認文で素通りしたこと (2026-10-02)。
- 余力があれば検討する追加の run (2026-10-02 時点では未決):
  - 人間が介入しない条件 (C、G−) の繰り返し回数を増やす。

## A と F− の比較で考える観点 (著者のメモ、2026-10-03。全 run の終了後に改めて検討する)

- Claude のたたき台 (luna-A と luna-F の比較): 結果を分けたのは関門の有無であり、issue のファイルと Git ではない。関門は、Worker 自身が抱いた疑問 (gb のパリティ) を解決につなげた。重要な欠陥を見つけたのは、Manager AI ではなく成果物の確認だった。ファイルと Git が支えるのは、正しさではなく追跡できること。
- 著者の補足:
  - issue のファイルには、何を行ったかの記録としての役割が大きい。
  - ワークフローを設計しやすいという点でも、ファイルとして置く意義がある。
  - 人間の手助けは、単純な数では測れない。「それがないと議論が破綻する」手助けは、1 つでも致命的になる。
- Sonnet 4.6 の run (G−、A、F−) の Worker は、Copilot CLI で動かす (2026-10-03)。
  - 5 月の Sonnet と Opus の run (thm01-04、X-04、X-06) は Copilot CLI だった。luna の run もすべて Copilot CLI である。Claude Code を使うと、モデルの比較にツールの違いが混ざる。
