#### Layer B: Oscillator expression engine

Use exact rational arithmetic via `fractions.Fraction`.

Internal representation:

- oscillator word = tuple of labels such as
  - `("a_1_p", "b_1_m")`
  - `("b_1_p", "b_1_p")`
  - `()` for the constant term
- linear combination = dictionary
  - `dict[tuple[str, ...], Fraction]`

Canonical oscillator ordering:

```text
a_1_p < a_1_m < b_1_p < b_1_m < b_2_p < b_2_m < ...
```

Core operations:

- normal-order multiplication of words
- addition/subtraction of linear combinations
- scalar multiplication by `Fraction`
- graded commutator

#### Layer C: Oscillator relations

The normal-order engine should implement:

1. **Fermionic CAR**
   - `a_1_p * a_1_p = 0`
   - `a_1_m * a_1_m = 0`
   - `a_1_m * a_1_p = 1 - a_1_p * a_1_m`

2. **Bosonic CCR**
   - bosons commute unless they are a conjugate pair
   - `b_i_m * b_j_p = b_j_p * b_i_m + δ_ij`

3. **Boson-fermion commutation**
   - `b_i_s * a_1_t = a_1_t * b_i_s`

### 4. Recommended mathematical conventions for implementation

I asked for a critique of the implementation plan before finalizing it.
The critique pointed out two real blind spots, so I am explicitly resolving them here.

#### 4.1 Normalization of `E_2del{k}_p/m`

I recommend implementing

- `E_2del{k}_p = (b_k^+)^2`
- `E_2del{k}_m = (b_k^-)^2`

with **no extra `1/2` factor**.

Reason:

1. That is the convention already approved in `handover/notation.md`.
2. That is also the convention adopted in `docs/json_schema_specification.md`.
3. Using `1/2` here would change structure constants systematically and would break consistency with the approved schema draft.

#### 4.2 Cartan decomposition must include the constant term

This is essential.

Because

```text
H_{n+1} = - b_n_p b_n_m - 1/2,
```

the decomposition routine must treat the empty oscillator word `()` as a real
basis monomial in intermediate calculations.

So the Cartan solver should:

1. represent each `H_k` as a linear combination that may include `()`
2. solve the Cartan decomposition over exact rationals
3. include constant terms when expressing brackets back in the basis

Without this, odd-odd brackets that produce constants will decompose incorrectly.

### 5. Proposed bracket algorithm

For each ordered pair `(X, Y)` of basis generators:

1. load their oscillator realizations
2. compute `XY`
3. compute `YX`
4. evaluate the graded commutator

```text
[X, Y} = XY - (-1)^(p(X)p(Y)) YX
```

5. normal-order the result
6. decompose the result into basis generators
7. emit **one JSON entry per non-zero basis component**

This last point matters: a single bracket can produce multiple `Z` terms, so the
JSON writer must emit multiple rows with the same `(X, Y)` and different `(Z, coeff)`.
