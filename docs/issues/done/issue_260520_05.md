## Proposal for Schema 2 gamma computation

### 1. Recommended computation method

I recommend computing the C(n+1) gamma structure by extending the existing
exact-rational word engine from `src/C_generators.py` with a **gb-linear correction layer**.

#### Core idea

For Schema 1, every bracket was computed in the undeformed oscillator algebra.
For Schema 2, we keep the same basis, parity map, and generator realizations, but
evaluate brackets using the deformed boson-fermion exchange rule from
`docs/math/C_inhomogeneous_definition.md`:

```text
[b_j^s, a_1^sigma] = - gb_{sigma,j,s} * kappa
```

Then:

1. compute the full deformed bracket of two generators
2. separate the **kappa-linear** part from the undeformed part
3. project that kappa-linear part onto the existing Schema 1 basis
4. record the resulting coefficients as the Schema 2 gamma data

So the practical definition is:

```text
[X, Y]_gamma = [X, Y]_0 + kappa * gamma(X, Y)
```

where `gamma(X, Y)` is extracted from the first-order deformation term.

### 2. Internal coefficient model

I do **not** recommend trying to store gamma corrections with plain `Fraction`
coefficients only. That was sufficient for Schema 1, but not for Schema 2.

Instead, the deformed normal-order engine should return:

1. the undeformed rational expression
2. a gb-linear correction of the form
   - signed sums of parameter labels such as
     - `gb_a1p_b1p`
     - `gb_a1m_b2m`

Concretely, I recommend representing the gamma part as:

```text
dict[basis_generator_name, dict[gb_label, Fraction]]
```

This keeps the output exactly first-order in the deformation parameters and
avoids mixing symbolic gb labels into the rational Layer 1 engine.

### 3. Recommended `gb_matrix` indexing

I recommend the following fixed matrix layout.

#### Rows

Rows correspond to the fermionic oscillator label:

1. `a_1_p`
2. `a_1_m`

#### Columns

Columns correspond to the bosonic oscillators in the same order already used in
Schema 1:

```text
b_1_p, b_1_m, b_2_p, b_2_m, ..., b_n_p, b_n_m
```

So the `gb_matrix` is a `2 x 2n` matrix with entries labeled:

```text
gb_a1p_b1p, gb_a1p_b1m, ..., gb_a1p_bnp, gb_a1p_bnm
gb_a1m_b1p, gb_a1m_b1m, ..., gb_a1m_bnp, gb_a1m_bnm
```

This indexing is the cleanest match to:

- the oscillator labels already adopted in `handover/notation.md`
- the explicit `2 x 2n` requirement in Issue I05-1
- the fermion/boson label split in `C_inhomogeneous_definition.md`

### 4. Sign convention options requiring human approval

The sign choice that needs approval is **how the leading minus sign is represented in data**.

#### Option A — literal mathematical sign (recommended)

Keep the document formula exactly:

```text
[b_j^s, a_1^sigma] = - gb_{sigma,j,s} * kappa
```

Under this option:

- the stored parameter labels are unsigned:
  - `gb_a1p_b1p`
  - `gb_a1p_b1m`
  - ...
- the minus sign is part of the exchange rule itself
- gamma coefficients inherit their signs from actual commutator evaluation

Why I recommend Option A:

1. it matches the math document literally
2. it keeps the JSON closest to the formal definition
3. it avoids hiding the sign convention inside renamed parameter symbols

#### Option B — absorbed-sign data convention

Absorb the leading minus sign into the stored parameter symbols.

That is, define new stored data entries `G_{sigma,j,s}` by

```text
G_{sigma,j,s} = - gb_{sigma,j,s}
```

so the exchange rule becomes

```text
[b_j^s, a_1^sigma] = + G_{sigma,j,s} * kappa
```

Why Option B is plausible:

1. downstream gamma rows may look visually simpler
2. every emitted coefficient is then the direct coefficient of the exchange rule

Why I do **not** recommend it:

1. it breaks direct fidelity to the mathematical definition file
2. it makes later comparisons to the docs harder
3. it hides the sign convention in the data layer instead of keeping it explicit

### 5. Important mathematical correction discovered during planning

The new math file still leaves one subtle point that must be handled carefully.

#### 5.1 `gamma(odd, odd)` is non-zero in general

The deformation does **not** only appear in odd-even brackets.

For two odd generators such as

```text
E_eps1_del1_pp = a_1^+ b_1^+
E_eps1_del1_mp = a_1^- b_1^+
```

their anticommutator requires moving a boson past a fermion, so the deformed
exchange rule contributes kappa-linear terms.

With Option A, one obtains:

```text
gamma(E_eps1_del1_pp, E_eps1_del1_mp)
= - gb_a1m_b1p * E_eps1_del1_pp
  - gb_a1p_b1p * E_eps1_del1_mp
```

So my implementation proposal will treat gamma as potentially non-zero for:

- `odd, odd`
- `odd, even`
- `even, odd`

and zero only for purely bosonic `even, even` pairs.

#### 5.2 `H_1` has two deformation sources

Because

```text
H_1 = a_1^+ a_1^- + b_1^+ b_1^-,
```

the deformed engine must apply the exchange rule to **both** words inside `H_1`,
not just the bosonic part. Otherwise the `gamma(X, H_1)` terms will be incomplete.

### 6. Schema-level parity bookkeeping note

There is one parity-bookkeeping inconsistency between the new math text and the
already-approved Schema 1 conventions.

`C_inhomogeneous_definition.md` says:

- `kappa` is odd
- `gb` parameters are parity 1

But then the right-hand side of

```text
[b_j^s, a_1^sigma] = - gb_{sigma,j,s} * kappa
```

would have parity `1 + 1 = 0`, while the left-hand side has parity `1`.

So for **Schema JSON bookkeeping**, I recommend keeping the already-approved
Schema 1 convention:

- `central_elements.kappa.parity = 0`
- `gb` parameters recorded with parity `1`

This is the only way to keep the exchange-relation data parity-consistent at the
schema layer without changing the existing Schema 1 central-element convention.

### 7. Proposed `inhomogeneous_deformation` field shape

I recommend Schema 2 add an `inhomogeneous_deformation` object with at least:

```json

  "gb_parameter_parity": 1,
  "gb_matrix": {
    "rows": ["a_1_p", "a_1_m"],
    "columns": ["b_1_p", "b_1_m", "...", "b_n_p", "b_n_m"],
    "entries": [
      ["gb_a1p_b1p", "gb_a1p_b1m", "..."],
      ["gb_a1m_b1p", "gb_a1m_b1m", "..."]
    ]
  },
  "gamma_matrix": [
    {
      "X": "E_eps1_del1_pp",
      "Y": "E_eps1_del1_mp",
      "Z": "E_eps1_del1_pp",
      "coeff": "-gb_a1m_b1p"
    }
  ]
}
```

I also recommend that `gamma_matrix` store one row per non-zero `(X, Y, Z)` term,
exactly mirroring the sparse-list style already used by `structure_constants`.
