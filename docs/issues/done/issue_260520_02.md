## Proposal for Schema 1 v5.0 extension for C(n+1)

### 1. Proposed top-level Schema 1 shape

I propose that the C(n+1) Schema 1 keep the B(0,n) v5.0 structure as much as possible, with one explicit addition:

```json
{
  "schema_version": "5.0",
  "algebra": { ... },
  "oscillator_generators": { ... },
  "oscillator_relations": { ... },
  "central_elements": { ... },
  "basis": { ... },
  "parity": { ... },
  "generator_realization": { ... },
  "structure_constants": { ... },
  "metadata": { ... }
}
```

Recommendation:

1. Keep all existing B-schema keys unchanged where possible.
2. Add `central_elements` as a new top-level key for C(n+1).
3. Keep the rest of Schema 1 backward-compatible in shape and naming style.

### 2. Proposed `algebra` field

I recommend using the same object shape as in B(0,n), with C-family values substituted.

Example for `C(3) = osp(2|4)` (that is, bosonic rank `n = 2`):

```json
{
  "family": "C",
  "m": 1,
  "n": 2,
  "cartan_type": "C(3)",
  "alternative_notation": {
    "osp": "osp(2|4)",
    "dimension_formula": "osp(2m|2n) with m=1"
  },
  "dimension": {
    "total": 19,
    "even": 11,
    "odd": 8
  }
}
```

Recommended conventions:

- `family = "C"`
- `m = 1`
- `n` continues to mean the **bosonic rank**
- `cartan_type = "C(n+1)"` in rendered form, so examples are:
  - `C(2)` for `n=1`
  - `C(3)` for `n=2`
  - `C(4)` for `n=3`
- dimensions use:
  - even = `2n^2 + n + 1`
  - odd = `4n`
  - total = `2n^2 + 5n + 1`

### 3. Proposed `oscillator_generators` field

The source notes contain a small naming inconsistency:

- one place says to use a `standard_fermion` key,
- another says to add a `fermions` key.

I recommend **`standard_fermion`** because it is the cleanest one-for-one replacement for B(0,n)'s `supplementary_fermion` object.

Proposed shape:

```json
{
  "standard_fermion": {
    "count": 2,
    "labels": ["a_1_p", "a_1_m"],
    "parity": 1,
    "relation": "{a_1_m, a_1_p} = 1",
    "description": "Standard fermionic pair a_1^± with canonical anticommutation relations."
  },
  "bosons": {
    "count": 4,
    "n": 2,
    "labels": ["b_1_p", "b_1_m", "b_2_p", "b_2_m"],
    "description": "Bosonic oscillators b_i^± with i=1,...,n"
  }
}
```

General rule:

- fermion labels are always `a_1_p`, `a_1_m`
- boson labels remain `b_k_p`, `b_k_m`
- `bosons.count = 2n`

### 4. Proposed `oscillator_relations` field

I recommend preserving the B-schema key layout where possible and replacing only the fermion-specific part.

Proposed shape:

```json
{
  "standard_fermion_anticommutators": {
    "description": "Canonical anticommutation relations for the standard fermionic pair",
    "relations": {
      "same_type": "{a_1^+, a_1^+} = 0 and {a_1^-, a_1^-} = 0",
      "conjugate_pair": "{a_1^-, a_1^+} = 1"
    }
  },
  "bosonic_commutators": {
    "description": "Canonical commutation relations for bosonic oscillators",
    "relations": {
      "same_type": "[b_i^±, b_j^±] = 0 for all i, j",
      "conjugate_pair": "[b_i^-, b_j^+] = δ_{ij}"
    }
  },
  "mixed_commutators": {
    "boson_fermion": "[b_i^s, a_1^t] = 0 for all i and s,t in {+,-}"
  }
}
```

Recommendation:

- keep the existing `bosonic_commutators` and `mixed_commutators` key names
- replace `supplementary_fermion_relation` with `standard_fermion_anticommutators`
- do **not** encode deformation data here; keep Schema 1 focused on the undeformed oscillator algebra

### 5. Proposed `central_elements` field

I recommend making `central_elements` explicit for C(n+1), with both `kappa` and `K` recorded.

Proposed shape:

```json
{
  "kappa": {
    "parity": 0,
    "relation": "kappa^2 = 0",
    "description": "Formal central symbol for the nilpotent extension; recorded explicitly in the schema and excluded from basis lists."
  },
  "K": {
    "parity": 0,
    "relation": "K = 1",
    "description": "Central identity element; recorded for completeness and excluded from basis lists."
  }
}
```

Rationale:

1. This matches the existing B-side note that `kappa` is stored as parity `0` in JSON even though it is mathematically odd in the deformation discussion.
2. `K` should be present for schema completeness but excluded from PBW ordering and basis arrays.
3. This keeps Schema 1 self-describing without forcing the basis lists to include formal central identities.

### 6. Compatibility notes relative to the B(m,n) schema

I recommend the following compatibility policy:

1. Keep `schema_version = "5.0"`.
2. Keep the object shapes of `algebra`, `basis`, `parity`, `generator_realization`, `structure_constants`, and `metadata`.
3. Reuse the `bosons` object shape unchanged.
4. Replace only the B-specific auxiliary-fermion components with C-specific CAR components.
5. Add `central_elements` as the only new top-level key needed for the C specification draft.

In short:

- **same schema family shape**
- **same naming style**
- **different fermionic sector**
- **one new explicit top-level key: `central_elements`**

### 7. File naming convention

I recommend fixing the file naming rule exactly as follows:

- Schema 1: `C_n_structure.json`
- here `n` means the **bosonic rank**, not the Cartan label `n+1`

So the concrete files are:

- `C_1_structure.json` for `C(2) = osp(2|2)`
- `C_2_structure.json` for `C(3) = osp(2|4)`
- `C_3_structure.json` for `C(4) = osp(2|6)`

For later layers, the same rule should continue:

- `C_n_gamma.json`
- `C_n_evaluated_<gb>.json`
- `C_n_coboundary_<gb>.json`
