## Context & Background
The existing Schema 1 (algebra structure) was designed for B(m,n). Extending to
C(n+1) requires modifications to several fields while maintaining backward
compatibility. Issue I01 has finalized the basis and PBW ordering.

## Requirements
1. Design `algebra` field for C(n+1) (family="C").
2. Design `oscillator_generators` without supplementary fermion.
3. Design `oscillator_relations` for standard fermionic pair (CAR).
4. Determine `central_elements` (kappa, K) for C(n+1).
5. Define file naming conventions (e.g., `C_1_structure.json`, `C_2_structure.json`, `C_3_structure.json`).

### Mandatory unified rules (fixed for all runs)
- **Algebra Field**: explicitly include `"m": 1` and the dimension formulas `even`: `2n^2 + n + 1`, `odd`: `4n`.
- **Oscillator Generators**: two keys, `"fermions"` (with `m=1`, labels `a_1_p, a_1_m`) and `"bosons"` (with rank `n`).
- **Central Elements**: `central_elements` is a **top-level key**, containing `kappa` (parity 1) and `K` (parity 0).
- **File Naming**: `C_{n}_structure.json`, where `n` is the bosonic rank (e.g., C(2) uses `n=1`).

### Response

**Status**: done.

**Deliverable.** `docs/json_schema_specification.md` (new file, C(n+1) layout). It follows the B(0,n) v5.0 key order and nesting. Schema 2–4 layouts are also specified, because I05–I07 write them.

**Mandatory rules applied.**
- `algebra` has `"m": 1` and the dimension formulas even $2n^2+n+1$, odd $4n$ (also recorded numerically for $n=1,2,3$).
- `oscillator_generators` has two keys: `fermions` (`m=1`, labels `a_1_p`, `a_1_m`) and `bosons` (rank `n`). `supplementary_fermion` is removed.
- `central_elements` is a top-level key with `kappa` (parity 1) and `K` (parity 0).
- File naming is `C_{n}_structure.json`, with $n$ the bosonic rank.

**Choices and reasons.**
- Rationals are stored as strings (`"1/2"`), never floats, so the JSON is exact and reproducible.
- `structure_constants` lists every ordered pair with a non-zero bracket. Both $[X,Y]$ and $[Y,X]$ appear. This is simpler to check than the B(0,n) convention and removes the need to apply the sign rule when reading the file.
- `generator_realization` uses the same word notation as B(0,n) (`a_1_p`, `b_1_m`, …), with the normal-ordering rule stated explicitly.

**Compatibility.** A table in §2 maps each B(0,n) key to its C(n+1) value. The key set and nesting are the same, so the two files can be compared key by key.

**Open points carried forward.** The $K$-components of $\gamma$ (decision A4 in notation.md) are recorded in a separate `K_components` list in Schema 2 and Schema 3, not in the g-valued `entries`.
