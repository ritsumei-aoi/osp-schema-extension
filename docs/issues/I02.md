## Context & Background
The existing Schema 1 (algebra structure) was designed for B(m,n). Extending to
C(n+1) requires modifications to several fields while maintaining backward
compatibility. Issue I01 has finalized the basis and PBW ordering.

## Requirements
1. Design `algebra` field for C(n+1) (family="C").
2. Design `oscillator_generators` without supplementary fermion.
3. Design `oscillator_relations` for standard fermionic pair (CAR).
4. Determine `central_elements` (kappa, K) for C(n+1).
5. Define file naming conventions (e.g., `C_1_structure.json`, `C_2_structure.json`, `C_3_structure.json`).

### Mandatory unified rules (fixed for all runs)
- **Algebra Field**: explicitly include `"m": 1` and the dimension formulas `even`: `2n^2 + n + 1`, `odd`: `4n`.
- **Oscillator Generators**: two keys, `"fermions"` (with `m=1`, labels `a_1_p, a_1_m`) and `"bosons"` (with rank `n`).
- **Central Elements**: `central_elements` is a **top-level key**, containing `kappa` (parity 1) and `K` (parity 0).
- **File Naming**: `C_{n}_structure.json`, where `n` is the bosonic rank (e.g., C(2) uses `n=1`).

#### 3. Decisions taken

**(a) `schema_version` stays `"5.0"` (not bumped to 5.1/6.0).**
Options considered: bump to `"5.1"` to flag the new `central_elements` key;
bump to `"6.0"` to flag the removal of `supplementary_fermion`; keep `"5.0"`.
Chosen: keep `"5.0"`. The issue header calls this a "Schema 1 v5.0 extension",
and `B0n_schema_v5.md` directs that the C(n+1) output be "a complete equivalent
schema" at v5.0. Every structural change is either additive (a new key) or
confined to a B-specific object that has no C analogue; no retained key changes
type or cardinality. Bumping the version would wrongly suggest B files need
regeneration.

**(b) `kappa` parity = 1, contradicting `B0n_schema_v5.md` §`basis`/§3.**
`B0n_schema_v5.md` says κ is "listed as a central element with parity 0", but
`B0n_definition.md` §3 says $p(\kappa)=1$, and I02's mandatory rule says parity 1.
Options: follow the B schema text (parity 0); follow the B definition text and
the I02 rule (parity 1). **Chosen: parity 1.** It is the only value under which
$[X,Y]_\gamma = [X,Y]_0 + \kappa\,\gamma(X,Y)$ preserves total parity, it is
mandated by I02, and two of the three sources agree. The divergence is recorded
in-line in §1.6 of the specification so the audit trail is explicit.

**(c) Cartan labels `H_eps1` / `H_del{k}` instead of B's `H_1..H_n`.**
Options: keep positional `H_1,...,H_{n+1}` (Frappat simple-root order); use
root-indexed `H_eps1`, `H_del{k}`. Chosen: root-indexed, because C(n+1) has two
distinct Cartan sectors ($\mathfrak{so}(2)$ and $\mathfrak{sp}(2n)$) and
positional labels would hide which sector an index belongs to — which matters
directly in I05/I08, where only the $\varepsilon$ sector carries the deformation.

**(d) Storage convention for `structure_constants`: ordered pairs only.**
Options: store all $N^2$ ordered pairs; store only `pbw_index(X) <= pbw_index(Y)`.
Chosen: the latter, with graded antisymmetry implied and recorded in
`metadata.storage_convention`. This halves file size for $n=3$ and makes the
antisymmetry check of I04 a genuine test (reconstructing the other half) rather
than a tautology.

**(e) Added keys `dimension_formulas`, `even_subalgebra`, `rank`,
`normal_ordering`, `pbw_order`, per-realization `root`, and the extra `metadata`
convention fields.** All additive; justified because C(n+1) needs the
$\varepsilon$ vs $\delta$ distinction and the normal-ordering index map to be
machine-readable for Layers 2–4.

#### 4. File naming — confirmed

`data/C_1_structure.json` (C(2)), `data/C_2_structure.json` (C(3)),
`data/C_3_structure.json` (C(4)); likewise `_gamma`, `_evaluated_{profile}`,
`_coboundary`. Consistent with `B0n_schema_v5.md` and `handover/notation.md` §6.

#### 5. Compatibility with B(m,n) — documented

Specification §4 carries the full field-by-field table plus an explicit
compatibility statement: a B(0,n) v5.0 consumer that keys off `algebra.family`
and tolerates unknown keys reads C(n+1) files unchanged. The single required
code change is branching on `algebra.family` wherever `supplementary_fermion`
is hard-coded. Discriminator: `algebra.family` + `algebra.m`.
